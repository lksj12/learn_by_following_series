## 프로젝트 개요

여행 상품과 부가 옵션을 선택해 주문하는 React 애플리케이션을 만들고, 사용자 행동에 따라 화면과 금액이 올바르게 변경되는지 테스트했다.

주요 화면의 흐름은 다음과 같다.

1. 여행 상품의 수량과 부가 옵션을 선택한다.
2. 상품 금액과 옵션 금액, 전체 금액을 계산한다.
3. 주문 요약 화면에서 선택한 항목을 확인한다.
4. 약관에 동의한 후 주문을 확정한다.
5. 주문 완료 화면에서 주문번호와 주문 금액을 확인한다.
6. 첫 화면으로 돌아가 새로운 주문을 시작한다.

사용한 주요 도구는 React, Vite, Vitest, React Testing Library, user-event, MSW, Axios다. Express 서버는 상품과 옵션 데이터를 제공하고 주문 내역을 반환하는 역할로 사용했다.

## 역할을 기준으로 요소 찾기

React Testing Library에서는 구현 세부 정보보다 사용자가 화면을 인식하고 조작하는 방식에 가까운 쿼리를 사용했다.

- `input type="number"`는 `spinbutton` 역할로 찾았다.
- 체크박스는 `checkbox` 역할로 찾았다.
- 이미지에는 `img` 역할과 대체 텍스트를 사용했다.
- 버튼과 제목은 각각 `button`, `heading` 역할로 찾았다.

`getByRole("spinbutton", { name: "America" })`처럼 요소의 역할과 접근 가능한 이름을 함께 사용하려면 `label`과 `input`이 `htmlFor`와 `id`로 연결되어 있어야 한다. 테스트 코드는 화면의 동작뿐 아니라 마크업의 접근성까지 점검하는 역할을 했다.

## 동기 쿼리와 비동기 쿼리

화면에 이미 존재하는 요소는 `getBy...`로 조회하고, API 응답 이후 나타나는 요소는 `findBy...`로 조회했다.

- `getBy...`: 요소를 즉시 찾고, 없으면 바로 실패한다.
- `findBy...`: 요소가 나타날 때까지 비동기로 기다린다.
- `queryBy...`: 요소가 없어도 오류를 발생시키지 않으므로 사라졌는지 확인할 때 사용한다.

상품과 옵션은 API 요청 이후 렌더링되기 때문에 `findByRole`이 필요했다. 주문 완료 후 로딩 문구가 사라졌는지는 `queryByText`로 확인했다.

`await screen.getByRole(...)`처럼 동기 쿼리에 `await`만 붙이는 것으로는 대기 동작이 생기지 않는다. 비동기 렌더링을 기다려야 할 때는 쿼리 자체를 `findByRole`로 선택해야 한다.

## 사용자 행동 테스트

`user-event`로 실제 사용자와 유사한 입력 과정을 재현했다.

- 숫자 입력값을 지우고 새로운 수량을 입력했다.
- 옵션 체크박스를 선택하고 다시 해제했다.
- 주문 버튼과 확인 버튼을 클릭했다.
- 주문 완료 후 첫 페이지로 돌아가는 흐름을 확인했다.

`clear`, `type`, `click`은 비동기적으로 처리될 수 있으므로 `await`과 함께 사용했다. 사용자 입력이 끝나기 전에 합계를 검사하면 이전 상태인 `0`을 읽을 수 있기 때문이다.

## Context와 테스트용 렌더 함수

상품 수량, 옵션 선택 상태, 상품 합계, 옵션 합계, 전체 합계는 Context에서 관리했다. 상품과 옵션은 `Map`으로 저장하고, 항목 이름과 수량을 이용해 합계를 계산했다.

`OrderContextProvider`가 주문 상태와 상태 변경 함수를 Provider의 `value`로 전달하고, 필요한 컴포넌트가 `useContext(OrderContext)`로 값을 가져오는 구조를 사용했다. 이를 통해 여러 단계의 컴포넌트 사이에서 props를 계속 전달하지 않고도 동일한 주문 데이터를 공유할 수 있었다.

Context를 통한 데이터 흐름은 다음과 같다.

1. `Products`와 `Options`에서 사용자가 수량 또는 체크 상태를 변경한다.
2. `Type`이 Context의 `updateItemCount`를 호출해 상품 또는 옵션 상태를 갱신한다.
3. `OrderContextProvider`가 상품 합계, 옵션 합계, 전체 합계를 다시 계산한다.
4. `OrderPage`는 Context의 전체 금액을 표시한다.
5. `SummaryPage`는 같은 Context에서 선택 항목과 합계를 가져와 주문 내용을 보여 준다.
6. `CompletePage`는 Context의 주문 데이터를 서버에 전송하고, 첫 화면으로 돌아갈 때 주문 상태를 초기화한다.

이 구조에서 `OrderPage`, `SummaryPage`, `CompletePage`는 서로 직접 데이터를 전달하지 않는다. 각 컴포넌트가 공통 Provider에 연결되어 같은 주문 상태를 읽고 변경한다. 화면 단계가 바뀌어도 Provider가 유지되는 동안 선택한 상품과 계산된 금액도 유지된다.

각 상품과 옵션의 가격이 다르기 때문에 단순히 전체 수량에 하나의 가격을 곱하지 않고 다음 구조로 계산했다.

```js
for (const [itemName, count] of orderCounts[orderType].entries()) {
    subtotal += count * pricePerItem[orderType][itemName];
}
```

Context를 사용하는 컴포넌트를 Provider 없이 렌더링하면 `useContext`가 정상적인 값을 받지 못한다. 반복해서 Provider를 작성하지 않도록 `test-utils`에 사용자 정의 `render`를 만들고, 테스트 대상이 항상 `OrderContextProvider` 안에서 렌더링되도록 구성했다.

### Redux 대신 Context를 사용한 이유

이 프로젝트에서는 Redux를 사용하지 않고 React의 Context와 `useState`를 조합했다. 공유해야 하는 전역 상태가 주문 수량, 옵션 선택, 합계 정도로 한정되어 있고 상태 변경 흐름도 비교적 단순하기 때문이다. 별도의 상태 관리 라이브러리를 추가하지 않아도 React가 기본으로 제공하는 기능만으로 주문 화면 전체의 데이터를 공유할 수 있었다.

Context와 Redux는 모두 여러 컴포넌트가 상태를 공유할 때 사용할 수 있지만 역할과 범위에는 차이가 있다.

Context는 컴포넌트 트리 아래로 값을 전달하는 React의 기능이다. 자체적으로 상태 변경 규칙을 제공하는 상태 관리 도구라기보다는, `useState`나 `useReducer`로 만든 상태를 여러 컴포넌트에 전달하는 통로에 가깝다. 설정이 간단하고 추가 패키지가 필요하지 않아 규모가 크지 않은 전역 상태에 적합하다.

Redux는 애플리케이션 상태를 React 외부의 하나의 store에서 관리하는 전용 상태 관리 도구다. action과 reducer를 통해 상태 변경 흐름을 명확하게 구성할 수 있고, Redux DevTools를 이용해 변경 이력과 상태를 추적하기도 쉽다. 비동기 처리, 복잡한 상태 변경, 여러 도메인이 얽힌 대규모 애플리케이션에서 일관된 규칙을 유지하는 데 유리하다.

선택 기준을 정리하면 다음과 같다.

- 공유 상태가 적고 변경 흐름이 단순하면 Context만으로 충분할 수 있다.
- 많은 컴포넌트가 자주 변경되는 전역 상태를 구독하면 Context Provider의 값 변경으로 불필요한 재렌더링이 늘어날 수 있다.
- 상태 변경 규칙, 디버깅 도구, 미들웨어, 비동기 흐름 관리가 중요하면 Redux가 더 적합할 수 있다.
- Context와 Redux는 반드시 둘 중 하나만 선택해야 하는 관계는 아니다. 테마나 로그인 정보는 Context로, 복잡한 업무 상태는 Redux로 관리하는 방식처럼 함께 사용할 수도 있다.

이 프로젝트의 주문 상태 규모에서는 Context가 필요한 기능을 충분히 제공했고, Redux를 추가하면서 생기는 store, action, reducer 등의 설정 없이 테스트 대상의 데이터 흐름을 비교적 간결하게 유지할 수 있었다.

## MSW로 API 요청 테스트하기

MSW를 사용해 테스트 환경에서 상품, 옵션, 주문 API를 가로챘다. 실제 서버를 실행하지 않아도 컴포넌트가 네트워크 요청을 보낸 이후의 화면을 검증할 수 있었다.

테스트한 API 상황은 다음과 같다.

- 상품 목록 요청 성공
- 옵션 목록 요청 성공
- 상품 요청 실패 시 오류 배너 표시
- 주문 요청 후 주문번호와 금액 표시
- 주문 처리 중 로딩 화면 표시

프로젝트에서 사용한 MSW는 v2이므로 `rest.get()` 대신 `http.get()`과 `HttpResponse.json()`을 사용했다. 오류 응답이 필요한 테스트에서는 `server.resetHandlers()`로 해당 테스트에만 적용되는 500 응답 handler를 설정했다.

주문 완료 테스트에서는 mock 응답에 짧은 지연을 추가해 로딩 상태와 완료 상태를 각각 검증했다. 응답이 즉시 끝나면 테스트가 로딩 화면을 확인하기 전에 완료 화면으로 전환될 수 있기 때문이다.

## 단위 흐름에서 전체 주문 흐름까지

테스트 범위를 작은 단위부터 전체 흐름까지 확장했다.

- 상품 이미지와 옵션 체크박스 개수를 확인했다.
- 상품 수량 변경에 따른 상품 합계를 확인했다.
- 옵션 선택과 해제에 따른 옵션 합계를 확인했다.
- 상품과 옵션을 합한 전체 금액을 확인했다.
- 주문 화면에서 요약 화면, 완료 화면, 첫 화면까지 이어지는 전체 흐름을 확인했다.

통합 테스트에서는 America 2개, England 3개, Insurance 옵션을 선택한 뒤 상품 합계 `8000`, 옵션 합계 `500`, 전체 합계 `8500`이 각 화면에서 일관되게 유지되는지 검증했다.

## 테스트 과정에서 확인한 구현 세부사항

테스트 실패 원인을 따라가며 다음 구현 조건을 함께 점검했다.

- JSX를 포함한 파일은 `.jsx` 확장자를 사용한다.
- `map()`의 중괄호 본문에서는 JSX를 명시적으로 반환한다.
- 비동기 요청이 끝난 뒤 나타나는 요소는 `findBy...`로 찾는다.
- `user-event` 작업이 끝난 뒤 검증하도록 `await`을 사용한다.
- Context와 Provider의 export/import 이름을 일치시킨다.
- 라벨과 입력 요소를 연결해 접근 가능한 이름을 제공한다.
- mock 데이터와 실제 서버 데이터의 응답 구조를 동일하게 유지한다.
- 클라이언트가 전송하는 주문 데이터 구조와 서버가 읽는 경로를 일치시킨다.

테스트는 결과값만 확인하는 작업이 아니라 컴포넌트 구조, 상태 관리, 접근성, 비동기 처리, API 계약이 서로 맞물려 동작하는지 확인하는 과정이었다.

## 강의 분류에 대한 소감

강의가 백엔드로 분류되어 있다는 점은 다소 아쉬웠다. Express 서버는 대부분 제공된 코드를 붙여 넣어 상품·옵션·주문 데이터를 전달하는 보조 역할이었고, 실제 학습의 중심은 프론트엔드에 가까웠기 때문이다. 이미지와 옵션 데이터를 불러오고, 사용자 입력과 버튼 클릭에 따라 금액과 화면을 변경하며, 그 동작을 React Testing Library와 MSW로 검증하는 내용이 주요 비중을 차지했다. 따라서 강의 내용만 놓고 보면 `[프론트엔드] 리액트 테스트` 로 하는게 맞는것 같다.
## 정리

이 프로젝트에서는 개별 컴포넌트 테스트에서 시작해 실제 주문 과정 전체를 검증하는 통합 테스트까지 작성했다. 역할 기반 쿼리, 비동기 쿼리, 사용자 이벤트, Context Provider, API mocking을 하나의 흐름 안에서 사용하며 React 애플리케이션의 동작을 테스트 코드로 설명하는 방식을 다뤘다.

최종적으로 테스트는 단순히 오류를 찾는 장치가 아니라, 화면이 어떤 순서로 동작해야 하는지와 각 컴포넌트가 어떤 책임을 갖는지를 구체적으로 기록하는 실행 가능한 명세가 되었다.
